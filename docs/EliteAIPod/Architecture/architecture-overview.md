## Architecture Pattern

**Pattern:** modular_monolith

A modular monolith is the optimal pattern for this small-scale single-page guestbook application. The project scope is tightly bounded to three user stories covering message viewing, submission, and real-time feed update — all within a single deployment unit. Microservices would introduce unnecessary operational overhead (service discovery, inter-service networking, distributed tracing) for what is fundamentally a two-endpoint API backed by a single relational table. A pure monolith without module boundaries would work equally well at this scale, but adopting a modular structure (routes / services / repositories / models) enforces separation of concerns, makes the code easier to extend if the scope grows, and aligns with the sprint tasks (T-001 through T-006) that map cleanly to these layers. The chosen pattern also satisfies all NFRs: the single-process deployment easily handles the 10-concurrent-user scalability target, and the layered code organisation makes XSS sanitisation easy to enforce at a well-defined service boundary before persistence.

## Infrastructure

- **Deployment:** Single-host Docker Compose deployment: GuestbookAPI container (FastAPI via uvicorn), GuestbookFrontend container (React static files served via nginx), and MessageDatabase container (PostgreSQL 16). For production hosting, deploy to a cloud VM (e.g., AWS EC2 t3.micro or Render free tier) with a managed PostgreSQL instance. Static frontend assets can optionally be served from a CDN.
- **Scaling:** Vertical scaling on the single host is sufficient for the 10-concurrent-user target. For higher load, run multiple GuestbookAPI uvicorn workers behind nginx upstream load balancing. PostgreSQL connection pooling via pgbouncer if connection count grows. The stateless API design allows horizontal scaling without session affinity.
- **Caching:** none

## Security Considerations

- Server-side HTML/script tag stripping on POST /api/v1/messages before database persistence (bleach or markupsafe library) to prevent stored XSS
- React frontend renders message content exclusively via JSX text nodes (textContent semantics) — never innerHTML — to prevent DOM-based XSS
- Input length constraints enforced at both API validation layer (Pydantic) and database schema (varchar/text limits) to prevent buffer overflows and layout attacks
- HTTPS enforced in all non-local environments via nginx TLS termination to protect data in transit
- Safe error messages returned by the API — no stack traces or database details exposed to clients on 500 responses
- CORS policy on GuestbookAPI restricted to the known frontend origin to prevent cross-origin request forgery
