## ADR-001 — Use FastAPI as the backend framework

**Status:** accepted

**Context:** The project requires a REST API with two endpoints (GET and POST /messages) plus input validation and sanitisation. The framework must be compatible with SQLAlchemy 2.0 / Alembic and support Python async for future extensibility. The team needs automatic OpenAPI docs for frontend integration.

**Decision:** Adopt FastAPI 0.111 with Pydantic v2 for request/response validation, uvicorn as the ASGI server, and SQLAlchemy 2.0 as the ORM.

**Alternatives considered:**
- Flask — lacks native async, Pydantic integration requires extra wiring, no auto-generated OpenAPI docs
- Django REST Framework — significantly heavier, brings ORM/admin/auth overhead irrelevant to a two-endpoint guestbook
**Consequences:**
- Positive: native Pydantic validation eliminates boilerplate for T-003 request validation
- Positive: auto-generated /docs endpoint eases frontend integration testing
- Neutral: requires Python 3.10+ runtime
_Related: US-002, T-002, T-003_
## ADR-002 — Server-side HTML sanitisation to prevent stored XSS

**Status:** accepted

**Context:** The security NFR requires all user-submitted content to be sanitised before rendering to prevent Cross-Site Scripting attacks. The guestbook accepts free-text name and message fields from anonymous visitors and stores them in the database. The sprint risk register flags XSS as high-severity, noting that both server-side stripping and safe frontend rendering are required.

**Decision:** Sanitise name and message fields server-side using the bleach library (or markupsafe.escape) inside the MessageService layer before calling the repository. On the frontend, exclusively use React JSX text interpolation (which maps to textContent) — never dangerouslySetInnerHTML.

**Alternatives considered:**
- Client-side-only sanitisation — insufficient; a malicious client can bypass it and POST raw HTML directly to the API
- Content-Security-Policy only — reduces exploit impact but does not prevent injection into the database or rendering via non-browser clients
**Consequences:**
- Positive: stored XSS is eliminated at the persistence boundary regardless of frontend implementation
- Positive: dual-layer defence (server sanitise + textContent) satisfies the high-priority security NFR
- Neutral: bleach/markupsafe adds a minor dependency; strip-only mode has negligible performance cost
_Related: NFR-security, T-003, T-004, US-002_
## ADR-003 — Return full message object from POST /messages to enable optimistic feed update

**Status:** accepted

**Context:** US-003 requires the new message to appear at the top of the feed immediately after submission without a full page refresh. The sprint risk register identifies a medium-severity risk: if POST /messages returns only a success status, the frontend cannot prepend the new message without a refetch, introducing a round-trip delay and additional error surface.

**Decision:** POST /api/v1/messages must return HTTP 201 with the full created message object (id, name, message, created_at) in the response body. The frontend uses this object directly to prepend to the message list without a refetch.

**Alternatives considered:**
- Return 204 No Content and trigger a GET /messages refetch — adds latency and a second failure point
- Return only the new message id and reconstruct locally — cannot populate created_at accurately without a server timestamp
**Consequences:**
- Positive: US-003 feed update is instantaneous with a single network round-trip
- Positive: frontend and backend share a single source of truth for the created_at timestamp
- Neutral: response payload is slightly larger but negligible at this scale
_Related: US-003, T-003, T-006_
## ADR-004 — Use React 18 for the frontend single-page application

**Status:** accepted

**Context:** The frontend must implement a message timeline component (T-004), a submission form component (T-005), and integrate both with real-time state updates after submission (T-006). Client-side state includes messages list, loading/error flags, and isSubmitting boolean. Keyboard accessibility and safe text rendering are explicit acceptance criteria.

**Decision:** Build the SPA with React 18 using functional components and hooks (useState, useEffect). No external state management library is needed given the limited state surface. Use Vite as the build tool. Serve built static assets via nginx.

**Alternatives considered:**
- Vanilla HTML/JS with fetch — viable at this scope but manual DOM manipulation increases XSS risk when rendering message content
- Vue 3 — comparable, but React's JSX text interpolation is more explicit about preventing innerHTML and the team is more familiar with React
**Consequences:**
- Positive: React JSX text interpolation enforces textContent rendering, removing the XSS risk present in manual innerHTML manipulation
- Positive: component isolation makes T-004 and T-005 independently testable
- Neutral: adds a build step (Vite), but output is a static bundle easily served by nginx
_Related: US-001, US-002, US-003, T-004, T-005, T-006_
